### Deviations from Design

One documented, explicitly-authorized scope decision — not a deviation from any behavioral requirement:

- **`OutlookMailAdapter`'s signature extension is a stub, not real logic.** Per this batch's explicit instructions ("the REAL adapter implementation is Batch 2 [renumbered Phase 4 in tasks.md]... you may extend its signatures minimally if the Protocol change forces it — keep real logic changes to the next batch"), `OutlookMailAdapter.search()` now accepts `folder_path` but raises `NotImplementedError` immediately if it is non-`None` (never touches real `_FOLDER_MAP`/COM logic for it), and `get_message()` accepts `include_html` but does not yet read `HTMLBody` — `MessageDetail.html_body` stays `None` via the schema's own default, which required no adapter-side code at all. This is safe because: (a) no test in this batch or in the pre-existing `tests/test_mail_adapter.py` exercises `folder_path`/`include_html` on the real adapter — all 25 pre-existing `test_mail_adapter.py` tests call with keyword `date_from=`/`date_to=` (never positional), so inserting `folder_path` as the 2nd positional parameter did not shift any existing call; (b) Phase 4's tasks.md (4.1-4.10) is the explicitly designated place for the real traversal/DASL-skip/attachment/HTMLBody logic.

Everything else matches design.md's Interfaces/Contracts section and the mail-search/mail-get-detail/outlook-mail-adapter specs verbatim:
- `MailFolder` gains `DRAFTS = "drafts"` exactly as specified.
- `MailSearchRequest`'s `_exactly_one_folder_selector` validator matches design.md's code sketch verbatim (`(self.folder is None) == (self.folder_path is None)` raises `ValueError`).
- `GetMessageRequest.include_html_body`/`MessageDetail.attachment_names`/`MessageDetail.html_body` field names, aliases, and defaults match design.md's Interfaces/Contracts section verbatim.
- `MailPort.get_message()`'s adapter-level parameter is named `include_html` (not `include_html_body`), per design.md's Interfaces/Contracts code sketch — the schema-level field (`GetMessageRequest.include_html_body`, wire alias `includeHtmlBody`) and the adapter-level parameter (`include_html`) are deliberately named differently at their respective layers, matching design.md exactly; `tools/mail.py` is the seam that renames one to the other (`adapter.get_message(request.entry_id, include_html=request.include_html_body)`).
- `MailFolderNotFoundError`'s `code`/`path`/`failing_segment` shape matches the outlook-mail-adapter spec and design.md's "Exclusivity + errors" decision verbatim.
- `FakeMailAdapter`'s `folder_paths` dict-of-lists is the fake-layer stand-in for the real adapter's per-segment traversal — the fake reports the *whole* unresolved path as `failing_segment` (since it has no segments to walk), which is a reasonable simplification for a fake and does not contradict any spec scenario (none of this batch's or the mail-search spec's scenarios assert a specific `failing_segment` value narrower than the full path for the fake-adapter case — only the outlook-mail-adapter spec's real-adapter scenario, Phase 4, requires true per-segment identification).

### Deviations from Design

None — implementation matches design.md's Interfaces/Contracts, Data Flow, and Architecture Decisions sections verbatim:

- `_FOLDER_MAP[MailFolder.DRAFTS] = (16, "[LastModificationTime]", "drafts_folder_id")` matches the "Drafts date field" decision exactly.
- `_resolve_folder_path()` uses `namespace.DefaultStore.GetRootFolder()` (never `namespace.Folders`), matching the "Path root" decision — shared/other-store mailboxes remain unreachable by construction, not by a runtime check.
- Segment resolution via `current.Folders.Item(segment)` inside a per-segment `try`/`except` matches the "Segment resolution" decision (`.Item(name)`, not call-syntax or name-iteration).
- `search()`'s folder_path branch never calls `Restrict()` and instead fetches `target_folder.Items` directly, applying `_matches_date_bounds()` (built on `_resolve_date()`) per item in Python — matches the "folderPath date filtering" decision verbatim, including the explicit rationale that a custom folder's item types are unknown ahead of time.
- `get_message()`'s attachment loop is `range(1, item.Attachments.Count + 1)` with `.Item(i).FileName` — matches the "Attachment names" decision (1-indexed, `FileName` not `DisplayName`).
- `html_body = item.HTMLBody if include_html else None` matches the "HTML body opt-in" decision — `HTMLBody` is a plain conditional expression, never evaluated when `include_html` is falsy (confirmed by `test_html_body_not_accessed_unless_include_html_true`'s raising-property guard, not just by code inspection).
- The Sequence Diagram — folderPath Resolution's four-step traversal (`DefaultStore.GetRootFolder()` → `Folders.Item("Proyectos")` → `Folders.Item("2026")` → any `Item()` failure → `MailFolderNotFoundError`) is implemented as a straight line-for-line translation in `_resolve_folder_path()`.

One implementation decision not spelled out verbatim in design.md but consistent with its intent, worth flagging explicitly: for the **mapped `drafts` folder** (as opposed to `folder_path`), the per-item date extraction also uses `_resolve_date()`'s fallback chain (not a fixed `LastModificationTime` `getattr`), while `Restrict()` still narrows the COM-side result set on `[LastModificationTime]` alone. Rationale: the "Date Resolution Fallback Chain" spec requirement explicitly names "drafts, and any folder_path folder" as needing the fallback for date *resolution* (as opposed to the Restrict() DASL field, which is a separate, unambiguously single-field concern per the "Real Adapter COM Access Per Folder" requirement) — so a draft item that Outlook restricted via `LastModificationTime` but which also happens to have a populated `ReceivedTime`/`SentOn` should still prefer those per the fallback chain's stated precedence. This does not affect `inbox`/`sent`, which keep pure direct-field access with no fallback at all (task 4.9's explicit backward-compat guard).
